01 — Banking WEB Overview

What the frontend does 개요

Purpose. The Banking WEB module is the Next.js client for the Banking domain — it renders the account list, transaction ledger, transfer composer, reports and smart-organizer screens, drives live bank scraping through the local NXiSAS engine, and persists nothing but the auth token / user / locale in localStorage. It is a client-rendered SPA inside the Next.js 16 App Router: no SSR data fetching and no server actions — every Banking screen gets its data from wecms-api over Axios, and Banking defines no Next.js route handler of its own. (App-wide there is exactly one Next.js route handler in source — the overseas-payment Excel preview — and it is not on the runtime path; see docs/README.md § Architecture facts. The earlier blanket “no Next.js API routes” wording was corrected 2026-08-17.)

This document vs. the API document. The companion API Banking Flow doc explains the Spring Boot backend logic (services, tables, DB functions). This doc explains the frontend: routes, components, hooks, state, search/filter/grid behavior, buttons/actions, loading/empty/error states, validation, and how each screen calls the API.

Architecture in one line. A thin page.tsx composes a feature component → a client wrapper owns state (useApiData + useTableSort + usePagination + useViewSetting) → an lib/api/* fetcher unwraps the ApiResponse<T> envelope → a lib/api/mappers.ts mapper translates snake_case wire → camelCase in-memory → the grid renders.

Conventions that govern every screen. Wire = lowercase snake_case; in-memory = camelCase semantic; all text via t(…) (EN/KO/VI); all amounts via formatAmount(value, ccy) from lib/currency.ts; all typography via WB365 Tailwind tokens (text-wb-*); shared components only (reuse before create).

UI render state / handler API call external (bank engine) result
  • Menu Click → Page Load. Routes are slug-based under app/(dashboard)/banking/… — the dashboard layout's client auth guard runs fetchMe() before the page mounts; an invalid token redirects to /login.
  • Search Condition. Filters, sort cycle, and pagination are React state owned by the client wrapper. A filter change calls resetPage() (page → 0) and re-fires the fetch via the useApiData dependency array.
  • API Request → Grid Render. Fetchers unwrap { status, data }, throw ApiCallError on status.error, and map snake_case → camelCase at the boundary. While loading, prior rows latch (sticky loading) so the grid never flashes empty.
  • User Action → Result Update. Mutations (confirm, classify, sync, transfer-result intake) re-fetch or bump a refreshKey; the grid re-renders with the new data. Errors route to useDialog({ type: "error" }).

06 — Internal Transfer (VND) UI Flow

The boundary contract

  • Envelope: { status: { error, code, message }, data } (+ trace_id on errors). HTTP 200 alone is not success — always check status.error.
  • Wire types in lib/types/api.ts are lowercase snake_case; in-memory types are camelCase semantic.
  • Translation happens once in lib/api/mappers.ts (and lib/auth/client.ts) — components never read response.data.user_id directly.
  • Errors: ApiCallError(code, message, traceId) → useDialog({ type: "error", errorCode }); 401 handled centrally by the Axios interceptor + session-expired flow.

Query / param conventions

  • Params lowercase snake_case: page, size, sort_field, sort_direction, from_dt, to_dt, keyword, bank_cd, currency.
  • New list clients send page (0-based) + size; grandfathered ones (transfer history) use page_no/page_per_cnt.
  • Dates: wire yyyyMMdd (no hyphens) / in-memory YYYY-MM-DD; formatted for display via lib/datetime.ts.
  • Binary export/download bypasses unwrap() — consumed via lib/excel.ts / lib/file.ts (blob).

13 — Validation & Error Display

States & client validation 검증 · 오류 표시

Loading
useStickyLoading gate; prior rows latch, centered "Loading…"; action buttons disabled while async.
Empty result
Friendly t(...) message (e.g. account_inquiry.empty_vnd, transfer_history.empty.default); reports show a Search-gate placeholder.
Error
Load errors → inline ErrorBanner (transfer history) or sticky-resolved inline; action errors → useDialog({ type:"error", errorCode, traceId }).
Success
Mutation → success dialog (where Figma shows one) → refetch / refreshKey bump; grid reflects the change.

Client-side validation

  • Account Inquiry: checkboxes disabled for manual (hand_reg_yn='Y') and disconnected (cert_conn_yn='N') accounts; filters always reset page to 0.
  • Transfer composer: amount > 0; target required; not self-transfer; transfer type shape (SAME_BANK needs target bank / NAPAS needs NAPAS code → validateNapas); per-bank password rule + remark byte-limit (from bank-profiles.ts).
  • Transfer History: to_dt ≥ from_dt (surfaced via backend code if violated).
  • Smart Organizer rule: remark required, max 500 chars.

Error display rules

  • One funnel: ApiCallError carries { code, message, traceId }; the system error dialog renders the trace_id verbatim.
  • Never a bespoke per-page error banner for system errors — use useDialog(); never render "UNKNOWN" without a code.
  • Dialog variant must match: API/validation failures → type:"error" (red), not "warning".
  • 401 → central Axios interceptor → session-expired dialog → re-login (no per-call 401 handling).

Menu visibility (frontend)

  • Sidebar + top-nav are backend-driven via useNavigation() → GET /api/v1/navigation — hardcoded menu arrays were removed.
  • The tree is the product tree (F/M/H) intersected with the user's grants; admins get the full product tree.
  • Product H drops Daily Cash / Daily Financial CMC / Cash Flow and gains Daily Financial (HS); F/M are structurally identical (M differs only in VI/KO labels).

Enforcement boundary

  • Frontend visibility is UX only, never the boundary — every API call is gated server-side by @menuAuthz; a denied call returns 403 (WBE1003).
  • Action-level (R/D/T) gating is a static {R:true,D:true,T:true} stub pending backend gate R-02 — UX only, not security.
  • Tenant + product type come from the signed JWT (StoredUser is display-only) — the frontend never sends biz_key/prdt_type outside login.
